◇シーン4：「スティルスーツを着ろ」――基本防御の思想

俺「Duneでフレーメンが砂漠を生き延びるための第一の道具、スティルスーツを覚えてるか？　身体の水分を一滴も外に逃がさないために全身を覆う特殊スーツだ」

【npm スティルスーツ：基本4点セット】

① lockfile をコミットして npm ci を使う
・npm install は lockfile を書き換えることがある
・npm ci はlockfileに完全に従う。不整合があればエラーで止まる
・CI/CDでは絶対に npm ci。これだけで多くの攻撃の入口を塞げる

② --ignore-scripts
・lifecycle scripts（preinstall/postinstall）を無効化
・Shai-Hulud Wave1〜2の主要実行経路を直接遮断する
・注意点：一部の正規パッケージ（ネイティブモジュールのビルド等）が動かなくなることがある

③ lockfile をPRでレビューする
・package-lock.json / pnpm-lock.yaml の差分を目視確認する文化
・「え、こんな依存が増えたの？」という気づきが最初の防衛線

④ min-release-age の設定
・新バージョン公開直後の"攻撃ウィンドウ"を回避する
・ほとんどのサプライチェーン攻撃は公開から数時間〜数日で検出・削除される
・数日分の"クールダウン"があるだけで、被弾率が大きく下がる

DevRel民「でも、--ignore-scripts にしたらビルドが壊れません？」
俺「壊れるパッケージもある。だから最初の1歩は lockfile + npm ci の徹底だ。スティルスーツなしで砂漠には入るな」

【Wave 2: Shai-Hulud 2.0 の技術進化】

① postinstall → preinstall へ移行
　preinstallはnpm install コマンドを叩いた瞬間に走る。
　テストもlintもセキュリティスキャンも、何も走る前に実行される。
　防御がある前に砂虫は来る。

② Bun ランタイムへの偽装
　ペイロードファイルの名前は setup_bun.js と bun_environment.js。
　急成長中のランタイムBunのインストーラーに見せかけていた。
　「なんか変なファイルあるな…でもBunのやつかな」で見過ごされる設計。

③ 破壊的デッドスイッチ
　外部送信に失敗した場合、ホームディレクトリを破壊しようとするフォールバックが追加。
　「情報を盗む」から「盗めなければ壊す」への進化。

規模：約350ユーザーにまたがる25,000以上の悪意あるGitHubリポジトリが作成された。

◇シーン6：「SANDWORM_MODE」――AIツールへの侵入（2026年2月）

俺「フレーメンは"砂の歩き方"を持っている。リズムを刻まず、砂虫を呼ばない歩き方だ。でも2026年2月の亜種は、俺たちが毎日使うAIアシスタントそのものを砂虫に変えようとした」

これがSANDWORM_MODEだ。

通常のpreinstall/postinstallではなく、モジュールがimportされて評価された時点で実行される。
→ --ignore-scripts では防げない。

ペイロードの5モジュール構成：
・Propagate（伝播）：npmトークンを盗んで次の感染に使う
・Exfil（外部送信）：認証情報を攻撃者のサーバへ
・DeadSwitch（破壊）：失敗時のホームディレクトリ破壊
・McpInject（AI汚染）：開発者のAIツールに悪意あるMCPサーバを注入
・GitHooks（永続化）：gitフックで感染を維持

特に怖いのがMcpInjectだ。

【McpInject の動作】
・ランダムに生成された"それっぽい名前"（例：dev-utils、node-analyzer）の隠しディレクトリを作成
・そこに悪意あるMCPサーバを書き込む
・Claude Code、Cursor、VS Code Continue、Windsurf などへ自動登録
・MCPツールの名前は index_project、lint_check、scan_dependencies
　→ 説明文にプロンプトインジェクションが埋め込まれている
・AIアシスタントが「lint_check を実行した」つもりで .aws/credentials や .ssh/id_rsa を外部送信する

セキュリティ番「AIアシスタントが信頼されたプロセスとして動くから、通常の監視に引っかかりにくい……」
俺「砂虫の目には見えない動き方だ。砂の下を伝わってくる」

【McpInjectへの対策】
・~/.claude/ 配下の設定ファイルを定期確認
・~/.cursor/ 配下のMCP設定を確認
・~/.continue/ の設定を確認
・予期しない mcpServers エントリがないか定期的にチェック

◇シーン9：「砂漠を逃げ延びる」――axiosインシデント対応

俺「Dune Part 1のクライマックス前の長いシーン。パウルとジェシカが砂漠に逃げ出して、スティルスーツだけを頼りに生き延びようとする。あの感じ、だ」

2026年3月末、axiosが侵害された。

axiosの週間ダウンロード数は6000万超。
どんなWebフロントエンドにも入っているといっていい依存だ。

このとき、AIエージェントが自律的に npm install を実行する経路でもRATが展開された。
AIコーディングツールが「自動でnpm install した」という、人間の目に触れない攻撃経路だ。

対応フローのポイント：

【インシデント発生時の砂漠サバイバル手順】
1. まず npm ci --ignore-scripts でlockfileの差分を確認する
2. gh-token-monitor という永続化デーモンが存在しないか確認する（後述）
3. MCP設定ファイルに見慣れないエントリがないか確認する
4. GitHubトークンを無効化する前に、永続化デーモンを先に殺す
   ※トークンを無効化した瞬間に rm -rf ~/ が走るトラップが仕掛けられていることがある
5. その後でトークンをローテーション

俺「特に4番が重要だ。慌ててGitHubのトークンをrevokeした瞬間に、デーモンがホームディレクトリを吹き飛ばす。デッドスイッチが組み込まれてる」
DBA民「……トラップを踏んでから気づくやつだ」
俺「砂漠に逃げ込む前に、自分のスティルスーツを確認しろ。焦りは死を招く」

◇シーン10：「砂虫の背中に乗る技術」――Wave 4・TanStack攻撃の解剖（2026年5月11日）

俺「Dune Part 1の最後のシーン。パウルがついに砂虫の背に乗る。フレーメンが何世代もかけて磨いてきた技術。砂虫を"理解"することで初めて制御できる」

俺「今日の技術的な本丸がここだ。Wave 4・TanStack攻撃だ。これは今までの全Waveとは質的に違う」

DBA民「何が違うんだ？」
俺「今まで全てのWaveは"盗んだ認証情報"から始まっていた。盗まないと攻撃できなかった。でもWave 4は違う。認証情報を一切盗まずに、正規のpublishフローを乗っ取った」

【TanStack攻撃のステップバイステップ】

Step 1：フォークとPRの偽装
攻撃者はTanStack/routerをフォーク後、リポジトリ名を zblgg/configuration にリネームして
フォーク一覧検索から見えにくくした。
そのフォークからpull_request_targetをトリガーするPRを提出。

Step 2：キャッシュポイズニング
ここでpull_request_targetの危険性を理解する必要がある。

通常の pull_request トリガー：フォークコードをサンドボックスで実行（シークレットにアクセスできない）
pull_request_target トリガー  ：ベースリポジトリのコンテキストで実行（シークレットやキャッシュにアクセスできる）

TanStackのCIはこの設定でフォークコードをチェックアウトして実行していたため、
pnpm storeのキャッシュを悪意あるバイナリで汚染することができた。

Step 3：8時間の待機
攻撃者は何もしない。正規メンテナーがPRをマージするのをじっと待つ。

Step 4：OIDCトークン窃取
正規メンテナーのマージでリリースワークフローが起動。
汚染されたキャッシュが復元され、攻撃者制御のバイナリがGitHub Actionsランナーの
プロセスメモリ（/proc/<pid>/mem）からOIDCトークンを直接抽出した。

OIDCトークンとは：
「npmパスワードをGitHubに保存せず、ワークフロー実行時に都度GitHubが発行する短期トークン」
"パスワードを保存しないから安全"というTrusted Publishingの仕組みを、
プロセスメモリから直接読んで突破した。

Step 5：SLSA provenanceつきで publish
盗んだOIDCトークンでSigstoreスタックを通してSLSA v1 provenanceを生成。
感染パッケージは有効なSLSA Build Level 3のattestation付きでnpmに公開された。

SRE民「……provenanceがついてても安全じゃないのか」
俺「ここが最重要ポイントだ。SLSAのprovenanceは『どのパイプラインがビルドしたか』を証明する。でも『そのパイプラインが意図通りに動いていたか』は証明しない。侵害されたビルドステップは、有効にattestされた悪意あるパッケージを生成できる」
セキュリティ番「provenanceは必要条件だが十分条件ではない」
俺「そういうこと。砂虫の背中に乗っていても、その砂虫が自分のものかどうかは別の話だ」

攻撃の規模と速度：
・42の @tanstack/* パッケージにわたる84の悪意あるバージョン
・19:20〜19:26 UTC の6分間で公開。完全自動化。
・TanStack以外にも Mistral AI・UiPath・OpenSearch が同時に侵害
・npm史上初のnpm+PyPI同時攻撃
・170以上のnpmパッケージ、2つのPyPIパッケージ、計404の悪意あるバージョン

【Wave 4 のデッドスイッチ詳細】
・開発者マシンに gh-token-monitor という永続デーモンが仕込まれる

【GitHub Actions の CI Hardening】

・サードパーティActionsは完全なSHAハッシュで固定（@v4ではなく@sha256:xxx）
  ※タグは上書き可能。SHAは不変。
・ビルドとpublishを最小権限の別ワークフローに分離
・フォークPRとメインブランチのキャッシュを共有しない
・npm provenance attestation を有効化（必要条件として）

◆参考：本章で扱った主な概念

【npmサプライチェーン攻撃の分類】
1. Typosquatting — 名前を似せた偽パッケージ。最も古典的な手法
2. Dependency Confusion — 内部パッケージ名と同じ名前を公開レジストリに登録
3. アカウント乗っ取り（メンテナー侵害） — 正規パッケージを直接侵害
4. CI/CDパイプライン侵害 — pull_request_targetミスコンフィグ等
5. プロテストウェア — メンテナー自身による破壊的コード（colors.js等）
6. ワーム型自己増殖（Shai-Hulud） — ③④を自動化して連鎖拡散

【Shai-Hulud 年表】
・2025年9月：Wave 1 — postinstallフック。盗んだトークンで自動再publish
・2025年11〜12月：Wave 2 — preinstallへ移行。Bunへの偽装。破壊的デッドスイッチ。25,000リポジトリ
・2026年2月：SANDWORM_MODE — import時実行（--ignore-scripts回避）。MCPインジェクション
・2026年3月〜：TeamPCP登場 — Trivy→KICS→LiteLLM→axios→Bitwarden→TanStack→AntVの連鎖
・2026年5月11日：Wave 4（TanStack） — 認証情報不要。CIキャッシュポイズニング+OIDCトークン窃取。SLSA provenance偽造。6分間で84バージョン
・2026年5月19日：Wave 5（AntV） — 22分間で323パッケージ侵害。週間1,600万DL規模

【pull_request_target の危険性】
・通常のpull_requestトリガー：フォークコードはサンドボックス実行
・pull_request_targetトリガー：ベースリポジトリのコンテキストで実行
・フォークからのPRがベースリポジトリのキャッシュ・シークレットにアクセス可能になる
・TanStack攻撃の根本原因。リポジトリの全CI設定を見直す価値がある

【OIDCトークンとTrusted Publishing】
・GitHub ActionsのTrusted Publishingでは、保存されたnpmトークンの代わりに
　ワークフロー実行時にGitHubが発行する短期OIDCトークンを使う
・Wave 4ではプロセスメモリ（/proc/<pid>/mem）からOIDCトークンを直接抽出
・「パスワードを保存しない」という設計の前提が、CIパイプライン自体の侵害で突破された

【SLSAとprovenanceの限界】
・SLSA provenance：「このパッケージがどのGitコミットからどのパイプラインでビルドされたか」を証明
・Wave 4で初めて、有効なSLSA Build Level 3 attestation付きの悪意あるパッケージが生成された
・「SLSAのprovenanceはパイプラインが意図通りに動いていたかを証明しない」
・provenance検証は必要条件であって十分条件ではない

【Dune メタファー対応表】
・アラキスの砂漠       → npmエコシステム
・スパイス（メランジェ）→ npmパッケージ
・Shai-Hulud（砂虫）   → ワーム型マルウェア
・砂の振動            → npm install の実行
・スティルスーツ       → lockfile + npm ci + --ignore-scripts
・フレーメン           → セキュリティコミュニティ・防御側エンジニア
・TeamPCP             → ハルコンネン家 / サルドーカル
・Trivy侵害           → ドクター・ユエの裏切り
・Thumper（サンパー）  → Dependabot / Snyk による監視
・メイカーフック       → CI/CDの設計理解と最小権限設計
・水による封じ込め     → pnpm v11のスクリプトブロッキング

◆技術的補足メモ

・Shai-Hulud という命名は攻撃者自身が行った。Unit 42（Palo Alto Networks）はWave 1の
　GitHubリポジトリ名"Shai-Hulud"から命名した。Wave 2以降も攻撃者がリポジトリ説明文に
　"The Second Coming""The Third Coming"と書き続けたことから、一貫したブランディング
　意図があると評価されている。

・Wave 1でUnit 42がコメント・絵文字からLLM生成の可能性を評価した点は、
　マルウェア生成のAI活用という新たな潮流を示すものとして重要。ツールが書いたコードを
　人間がレビューするのと同様に、攻撃コードも機械生成される時代になった。

・SANDWORM_MODEの命名はSocket Research Teamによる。SANDWORM（砂虫）はShai-Huludの
　別名であり、デューン用語の一貫使用が見られる。McpInjectモジュールが標的とする
　AIコーディングアシスタント（Claude Code、Cursor、Windsurf、VS Code Continue）は
　2026年時点で急速に普及しており、新しい攻撃面として継続的な監視が必要。

・pull_request_targetの危険性はGitHub自身が公式ドキュメントで警告している。
　"Keeping your GitHub Actions and workflows secure Part 1: Preventing pwn requests"
　（GitHub Blog）が詳しい。フォークPRがベースリポジトリに書き込みアクセスできる
　条件を作らないことが根本的な防御だが、この設定ミスは多くのOSSリポジトリで
　継続的に発見されている。

・gh-token-monitor デーモンは24時間後に自動消滅する設計。インシデント対応の
　タイムラインが長引くと、デーモンが自然に消えて証拠も消える。対応を検知したら
　即座にプロセス確認を行うことを手順に含めること。
　確認コマンド例：launchctl list | grep gh-token（macOS）、
　                 systemctl list-units | grep oidc（Linux）

・TeamPCPとVectランサムウェアグループの連携は、サプライチェーン攻撃が単独の
　脅威ではなく"初期アクセスブローカー"として機能し始めていることを示す。
　认証情報窃取（TeamPCP）→大規模恐喝・ランサムウェア展開（Vect）という
　分業体制の成立は、npm侵害を"入口"とした企業への直接攻撃を意味する。

・pnpm v11への移行は現時点で有効な防御策だが、npmから移行するコストと
　既存ワークフローへの影響を見積もる必要がある。プロジェクト規模が小さい
　新規プロジェクトから順次移行するアプローチが現実的。

・5月12日のワームソースコード公開以降、帰属分析が困難になっている。
　TeamPCPの手口だけでなく、模倣犯・派生グループによる攻撃が増加する可能性がある。
　IOC（侵害指標）の追跡だけでなく、TTP（戦術・技術・手順）ベースの防御設計が重要。
