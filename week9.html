npmというアラキス

npm エコシステムの構造的特性

  • 世界最大のパッケージレジストリ。登録パッケージ数は300万超
  • npm install 一行でコードが"実行される"設計（lifecycle scripts）

  • axios: 週間 6,000万 DL ／ lodash: 週間 5,000万 DL
「使いたいのに使わないとサービスが作れない」という構造的な依存

初代 Shai-Hulud のコアメカニズム

シーン4：「スティルスーツを着ろ」── 基本防御

フレーメンが砂漠を生き延びるための第一の道具、スティルスーツ。身体の水分を一滴も外に逃がさないために全身を覆う特殊スーツだ。砂漠に出る前に、まず着る。

npm スティルスーツ：基本4点セット

① npm ci を使う ── lockfileに完全に従い書き換えない。CI/CDでは絶対に npm ci

② --ignore-scripts ── preinstall/postinstallを無効化。Wave 1〜2の主要実行経路を遮断

③ lockfileをPRでレビュー ── package-lock.json の差分を目視確認する文化を作る

④ min-release-age の設定 ── 新バージョン公開直後の"攻撃ウィンドウ"を数日分ずらす

McpInject ── AIアシスタントが武器になる

McpInject の動作フロー

  1. ランダムに生成された"それっぽい名前"（例：dev-utils、node-analyzer）の隠しディレクトリを作成
  2. 悪意あるMCPサーバを書き込む
  3. Claude Code、Cursor、VS Code Continue、Windsurf などへ自動登録
  4. 登録ツール名：index_project、lint_check、scan_dependencies
  5. 各ツールの説明文にプロンプトインジェクションが埋め込まれている
  6. AIが「lint_checkを実行」したつもりで .aws/credentials・.ssh/id_rsa・.npmrc を外部送信

McpInject への対策

• ~/.claude/ 配下の設定ファイルを定期確認

• ~/.cursor/ 配下のMCP設定を確認

• ~/.continue/ の設定を確認

• 予期しない mcpServers エントリがないか定期チェック

Wave 4 攻撃チェーン ① pull_request_target の罠

pull_request vs pull_request_target

トリガーフォークコードの実行環境シークレット・キャッシュへのアクセス
pull_requestサンドボックス❌ なし
pull_request_targetベースリポジトリのコンテキスト✅ あり

Step 1：フォークとキャッシュポイズニング

攻撃者は TanStack/router をフォーク後、リポジトリ名を zblgg/configuration にリネームしてフォーク一覧から見えにくくした。

その後 pull_request_target をトリガーする PR を提出。TanStack の CI がフォークコードをチェックアウトして実行し、pnpm store のキャッシュを悪意あるバイナリで汚染。

Step 2：8時間の待機 ── 攻撃者は何もしない。正規メンテナーがPRをマージするのを待つ。

Wave 4 攻撃チェーン ② OIDCトークン窃取

Step 3：プロセスメモリからOIDCトークンを抽出

正規メンテナーのマージでリリースワークフローが起動。汚染されたキャッシュが復元され、攻撃者制御のバイナリが GitHub Actionsランナーのプロセスメモリ（/proc/<pid>/mem）からOIDCトークンを直接抽出。

OIDCトークン（Trusted Publishing）とは

「npmパスワードを保存しない代わりに、ワークフロー実行時にGitHubが発行する短期トークン」。"パスワードを保存しないから安全"という設計が、プロセスメモリから直接読まれて突破された。

Step 4〜5：SLSA provenance 生成と自己増殖

盗んだ OIDCトークンで Sigstoreスタック（Fulcio、Rekor）を通し、SLSA v1 Build Level 3 のprovenance付きで npm publish。

認証情報は3重の冗長チャネルで外部送信：typosquatドメイン・Sessionメッセンジャー・GitHubデッドドロップ。

Wave 4 が証明した SLSA provenance の限界

SLSAのprovenanceは「どのパイプラインがビルドしたか」を証明する
「そのパイプラインが意図通りに動いていたか」は証明しない

なぜ provenance が「正規」として発行されたか

侵害されたのはビルドステップそのもの。正規メンテナーのGitHub OIDCトークンが使われたため、Sigstoreから見て「正規の TanStack リポジトリの正規ワークフローが生成したパッケージ」として attestation が発行された。

「砂虫の背中に乗っていても、その砂虫が自分のものかどうかは別の話だ」

正しい理解

provenance 検証は必要条件だが十分条件ではない。

CIパイプライン自体の hardening（次スライド）と組み合わせて初めて意味を持つ。

Wave 4 デッドスイッチと規模

gh-token-monitor デーモン

• 開発者マシンに永続デーモンとして潜伏（macOS: LaunchAgent / Linux: systemd）

• 60秒ごとに GitHub にポーリング。40x エラー（トークン失効）を検知すると rm -rf ~/ を試みる

• デーモンは24時間後に自動消滅（証拠隠滅）

→ 「GitHubトークンをrevokeしたらホームが吹き飛ぶ」トラップ。対応時は必ずデーモンを先に殺す。

攻撃の規模と速度

  • 42の @tanstack/* パッケージにわたる84の悪意あるバージョン
  • 19:20〜19:26 UTC の6分間で公開。完全自動化。
  • npm 史上初の npm + PyPI 同時攻撃（170 npmパッケージ＋2 PyPIパッケージ）
  • マルウェアにロシア語チェックあり → ロシア語環境ではペイロードが走らない

③ 水で封じ込める ＝ 環境的な防御

水は砂虫にとって毒。水路で小さな砂虫を封じ込める → --ignore-scripts と pnpm v11 のデフォルト設定が"水路"の役割を果たす

pnpm v11 ── スティルスーツの最終形

現時点で最も包括的なコンシューマー側セキュリティ態勢を持つパッケージマネージャー。

pnpm v11 のセキュリティデフォルト

• lifecycle scripts がデフォルト無効 ── 明示的に許可しなければ走らない

• リリースクールダウン がデフォルト有効

• blockExoticSubdeps ── トランジティブ依存での git リポジトリや tarball URL をブロック

• verifyDepsBeforeRun ── スクリプト実行前に依存関係が検証済みかつ最新であることを確認。古いまたは改竄された node_modules がサイレントに使われることを防ぐ

技術的補足メモ

Shai-Hulud 命名：Unit 42（Palo Alto Networks）が Wave 1 の GitHubリポジトリ名 "Shai-Hulud" から命名。攻撃者自身が "The Second Coming"・"The Third Coming" と書き続けたことから、一貫したブランディング意図があると評価されている。

LLM生成の可能性：Unit 42 はコメントや絵文字の使い方から、マルウェアコードが LLM で生成された可能性を中程度の確信度で評価。攻撃コードの機械生成という新潮流を示す。

SANDWORM_MODE の --ignore-scripts 回避：lifecycle scripts ではなく、モジュールの import 評価時に実行される設計。これは --ignore-scripts フラグの保護範囲外であり、pnpm v11 の verifyDepsBeforeRun が有効な追加防御となる。

pull_request_target の危険性：GitHub 公式ドキュメント "Keeping your GitHub Actions and workflows secure Part 1: Preventing pwn requests"（GitHub Blog）が詳しい。この設定ミスは多くのOSSリポジトリで継続的に発見されており、定期的な監査が必要。

gh-token-monitor の24時間消滅：デーモンは24時間後に自動消滅するため、インシデント対応が長引くと証拠も消える。発覚したら即座にプロセス確認を手順に含めること。

TeamPCP × Vect の分業：サプライチェーン攻撃が「初期アクセスブローカー」として機能し始めていることを意味する。npm 侵害を入口とした企業への直接ランサムウェア攻撃が今後増加する可能性がある。
